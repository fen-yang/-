## 二、WBS分解结果及其三级分解逻辑

### 2.1 WBS分解结果

我们将项目成果划分为3个主要成果域（一级），每个成果域进一步分解为子成果（二级）和最小管理单元（三级）。最终WBS结构如下：

```text

1.0 需求与设计成果
  1.1 需求规格说明
    1.1.1 功能需求清单
    1.1.2 非功能需求说明
    1.1.3 用户角色定义
  1.2 系统设计成果
    1.2.1 数据库设计文档
    1.2.2 API接口设计文档
    1.2.3 前端页面原型

2.0 核心功能开发成果
  2.1 活动管理模块
  2.2 学生报名模块
  2.3 审核管理模块
  2.4 签到管理模块
  2.5 统计报表模块

3.0 技术基础设施成果
  3.1 后端服务
  3.2 前端界面
  3.3 二维码服务
```
### 2.2 三级分解逻辑

- **一级条目（成果域）**：体现项目主要产出方向，如项目管理、需求设计、功能开发等。
- **二级条目（子成果）**：对一级成果的进一步细分，例如“项目启动文档”包含章程、分工、约定。
- **三级条目（最小管理单元）**：能够独立分配责任人、独立估算工作量、独立验收的成果单元，如“项目章程”文档。

### 4.2 分支策略

采用 `main` + `dev` + `feature/*` 分支模型：

- **main**：受保护分支，仅接受来自 `dev` 的合并，用于存放稳定版本。
- **dev**：日常集成分支，所有 `feature` 分支的合并目标。
- **feature/\***：功能/文档分支，如 `feature/charter`、`feature/wbs`、`feature/conflict` 等。

操作流程：从 `dev` 切出 `feature/xxx` → 完成工作 → PR到 `dev` → 计划负责人审批合并 → 删除 `feature` 分支 → 阶段性合并 `dev` 到 `main`。

### 4.3 提交与合并规则

- **提交信息格式**：`<type>: <subject>`，其中 `type` 包括 `docs`， `feat`， `fix`， `chore`， `merge`。
- **合并规则**：
  - `feature/*` → `dev`：由计划负责人审批，要求无冲突且提交规范。
  - `dev` → `main`：由项目经理审批，要求所有文档齐全。
- **版本标记**：每次合并到 `main` 后打标签，格式 `v1.0.0`。
- **主分支保护**：在GitHub中设置 `main` 分支要求PR、至少1人审核、禁止直接推送。
