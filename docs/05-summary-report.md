- **工期估算**：采用经验类比法，参考课程作业常规用时（文档类0.5~1天，设计类1~2天）。

### 4.2 分支策略

采用 `main` + `dev` + `feature/*` 分支模型：

- **main**：受保护分支，仅接受来自 `dev` 的合并，用于存放稳定版本。
- **dev**：日常集成分支，所有 `feature` 分支的合并目标。
- **feature/\***：功能/文档分支，如 `feature/charter`、`feature/wbs`、`feature/conflict` 等。

操作流程：从 `dev` 切出 `feature/xxx` → 完成工作 → PR到 `dev` → 计划负责人审批合并 → 删除 `feature` 分支 → 阶段性合并 `dev` 到 `main`。

### 4.3 提交与合并规则

- **提交信息格式**：`<type>: <subject>`，其中 `type` 包括 `docs`， `feat`， `fix`， `chore`， `merge`。
- **合并规则**：
  - `feature/*` → `dev`：由计划负责人审批，要求无冲突且提交规范。
  - `dev` → `main`：由项目经理审批，要求所有文档齐全。
- **版本标记**：每次合并到 `main` 后打标签，格式 `v1.0.0`。
- **主分支保护**：在GitHub中设置 `main` 分支要求PR、至少1人审核、禁止直接推送。

## 五、实验冲突

### 5.1 场景设计

| 成员 | 分支 | 修改内容 |
|------|------|----------|
| 任俊 | `feature/renjun-priority` | 二维码签到 → **P0**，活动发布 → P1 |
| 李佳豪 | `feature/lijiahao-priority` | 活动发布 → **P0**，二维码签到 → P1 |

**冲突位置**：`docs/conflict.md` 中的优先级表格

### 5.2 冲突产生过程

```bash
# 李佳豪先合并（无冲突）
git merge feature/lijiahao-priority ✅

# 任俊后合并（产生冲突）
git merge feature/renjun-priority ❌ CONFLICT
```
### 5.3 冲突解决过程

#### 5.3.1 冲突内容

打开 `docs/conflict.md`，看到以下冲突标记：

```markdown
<<<<<<< HEAD
| 活动发布 | P0 | 管理员可以发布活动信息（没有活动就没有签到） |
| 二维码签到 | P1 | 扫码完成签到 |
=======
| 活动发布 | P1 | 管理员可以发布活动信息 |
| 二维码签到 | P0 | 扫码完成签到（现场签到最重要） |
>>>>>>> feature/renjun-priority
```
#### 5.3.2 解决方案

双方讨论后决定：**活动发布和二维码签到都是系统核心功能，都设为 P0**。

#### 5.3.3 最终版本

| 功能 | 优先级 | 说明 |
|------|--------|------|
| 活动发布 | P0 | 管理员可以发布活动信息 |
| 学生报名 | P0 | 学生可以在线报名 |
| 名单审核 | P1 | 管理员审核报名资格 |
| 二维码签到 | P0 | 扫码完成签到 |
| 统计导出 | P1 | 导出签到数据 |

#### 5.3.4 解决命令

```bash
# 1. 编辑文件删除冲突标记，保留最终内容

# 2. 标记冲突已解决
git add docs/conflict.md

# 3. 提交合并
git commit -m "merge: 解决优先级冲突，将活动发布和二维码签到都设为P0"

# 4. 推送到远程
git push origin main
```
